## 1. Pipeline and artifacts

```
prepare_corpus.py    ──► data/clean/{train,val}/*.txt
train_tokenizer.py   ──► data/tokenized/tokenizer.json      (train split only)
encode.py            ──► data/tokenized/{train,val,tiny}.bin + meta.json
test_roundtrip.py    ──► pass / fail
train.py             ──► one row appended to results/runs.csv (rank 0 only)
                         + optional checkpoint .pt (--save_checkpoint)
check_correctness.py ──► fills the `valid` column of results/runs.csv
sample.py            ──► generated text from a checkpoint (stdout)
```

| Stage | Script | Slurm script | Reads | Writes |
|-------|--------|--------------|-------|--------|
| Corpus | `src/prepare_corpus.py` | `slurm/prep_data.sbatch` | Project Gutenberg (cached in `data/raw/`) | `data/raw/`, `data/clean/train/`, `data/clean/val/` |
| Tokenizer | `src/train_tokenizer.py` | `slurm/tokenize.sbatch` | `data/clean/train/` | `data/tokenized/tokenizer.json` |
| Encoding | `src/encode.py` | `slurm/tokenize.sbatch` | `data/clean/`, `tokenizer.json` | `train.bin`, `val.bin`, `tiny.bin`, `meta.json` |
| Round-trip check | `src/test_roundtrip.py` | `slurm/tokenize.sbatch` | all of the above | exit code |
| Training | `src/train.py` | `slurm/job_*.sbatch` | `data/tokenized/` | `results/runs.csv`; checkpoint `.pt` only with `--save_checkpoint` |
| Smoke test | `scripts/pipeline_tiny.sh` | `slurm/cpu_smoke.sbatch` | `data/raw/` | `data/tokenized_smoke/`, `results/smoke_runs.csv` |
| Correctness | `src/check_correctness.py` | none (run after each job) | `results/runs.csv` | `results/runs.csv` (`valid` only) |
| Text generation | `src/sample.py` | final-run job (step 13) | checkpoint `.pt`, `tokenizer.json` | stdout (redirect into the job log) |

Nothing under `data/raw/`, `data/clean/`, `data/tokenized/` or
`data/tokenized_smoke/` is committed; every stage is regenerated by its script.
Checkpoints (`*.pt`, `checkpoints/`) are not committed either: they are large and
can be regenerated by rerunning the job.

## 2. Data format

Full spec: `data/README.md` (corpus catalog, split, tokenization, per-work counts).
The parts other code depends on:

| Item | Value |
|------|-------|
| Clean text | UTF-8, one `.txt` per work; `data/clean/train/` (69 works), `data/clean/val/` (12 works, held out whole); per-work metadata in `data/clean/catalog.csv` |
| Tokenizer | Byte-level BPE, Hugging Face `tokenizers`, trained on the train split only |
| Vocabulary | **8,192** (not 8,000), including one special token |
| Special token | `<\|endoftext\|>` = id **0**, appended after every work |
| `.bin` format | flat little-endian **uint16** token ids, no header |
| Loading | `np.memmap(path, dtype=np.uint16, mode="r")` |
| `tiny.bin` | first 1,500,000 tokens of `train.bin` (a prefix) |
| `meta.json` | vocab size, dtype, EOT id, token count per split (`splits.<name>.tokens`), SHA-256 of every file (`tokenizer_sha256` is copied into checkpoints) |

Validation always reads `val.bin`, also when training on `tiny.bin`.

## 3. `train.py` command-line interface

These flag names and defaults are frozen. Defaults equal the baseline
(6 layers, 6 heads, width 384, seq 256, global batch 64; 13.87M parameters).

**Data**

| Flag | Default | Meaning |
|------|---------|---------|
| `--data_dir` | `data/tokenized` | directory with the `.bin` files and `meta.json` |
| `--dataset` | `train` | training stream: `train` or `tiny` |
| `--dummy_data` | off | random tokens instead of `.bin` files (development only). Without this flag, a missing `<dataset>.bin` or `val.bin` is an **error** (exit code 1, before any training or CSV row) |
| `--vocab_size` | from `meta.json`, else 8192 | |

**Model**

| Flag | Default |
|------|---------|
| `--n_layer` | 6 |
| `--n_head` | 6 |
| `--n_embd` | 384 |
| `--seq_len` | 256 |
| `--dropout` | 0.0 |

**Optimisation**

| Flag | Default | Meaning |
|------|---------|---------|
| `--global_batch` | 64 | sequences per optimizer step, fixed across world sizes |
| `--micro_batch` | `global_batch / world_size` | sequences per forward pass per rank; smaller values use gradient accumulation |
| `--max_steps` | 1000 | also the end of the cosine schedule, so it changes the loss at step 500 (see §5) |
| `--lr` / `--min_lr` | 6e-4 / 6e-5 | cosine schedule |
| `--warmup_steps` | 100 | **learning-rate** warm-up (not timing warm-up) |
| `--weight_decay` | 0.1 | |
| `--beta1` / `--beta2` | 0.9 / 0.95 | |
| `--grad_clip` | 1.0 | |

**Run**

| Flag | Default | Meaning |
|------|---------|---------|
| `--precision` | `fp32` | `fp32` or `bf16` (autocast) |
| `--device` | `auto` | `auto`, `cpu`, `cuda`, `cuda:N` |
| `--seed` | 1337 | |
| `--num_threads` | torch default | CPU threads (job E) |
| `--compile` | off | wrap the model in `torch.compile` for training (step 12). Validation and checkpoints use the plain model. The first steps include compile time, which `--timing_warmup` excludes. The row's `notes` say `COMPILED`; give the run an `--experiment` label ending in `_compile` |
| `--eval_interval` | 100 | validation every N steps; step 500 is always evaluated |
| `--eval_iters` | 20 | validation batches per evaluation |
| `--eval_batch` | `global_batch` | sequences per validation batch, independent of world size |
| `--log_interval` | 10 | |
| `--summary_json` | none | write the final summary dict here |

**Instrumentation and results**

| Flag | Default | Meaning |
|------|---------|---------|
| `--timing_warmup` | 20 | steps excluded from the timing medians (`warmup_steps` column) |
| `--comm_measure_steps` | 20 | `no_sync()` comparison pairs after training (DDP only; 0 skips) |
| `--runs_csv` | `results/runs.csv` | rank 0 appends here; `none` disables. Smoke and dev runs must pass `results/smoke_runs.csv` (or `none`), see §4 |
| `--job` | `dev` | `A`, `B`, `C`, `D`, `E`, `opt`, `final`, `smoke`, `dev` |
| `--experiment` | `<device>_ws<N>_<precision>` | short label, see §5 |
| `--notes` | empty | free text, prepended to the automatic notes |

**Checkpoints**

| Flag | Default | Meaning |
|------|---------|---------|
| `--save_checkpoint` | none | rank 0 saves the model to this `.pt` file at the end of the run. Off by default, so timing runs write nothing |
| `--checkpoint_interval` | 0 | also save every N steps, overwriting the same file (protects long runs against the time limit); 0 = only at the end. Needs `--save_checkpoint` |



A checkpoint is a dict saved with `torch.save`: `model` (state dict of the unwrapped
model, so it loads the same whatever the world size), `config` (`GPTConfig` as a
dict), `step`, `val_loss`, `tokenizer_sha256` (from `meta.json`) and `args` (the
simple-valued flags). It is written to `<path>.tmp` and then renamed, so a job killed
mid-save keeps the previous checkpoint. Saving happens outside the timed part of the
step. It stores no optimizer state, so a checkpoint is for generation, not for
resuming training.

**Profiling**

| Flag | Default | Meaning |
|------|---------|---------|
| `--profile` | off | rank 0 records a `torch.profiler` trace: waits `--timing_warmup` steps, 2 profiler warm-up steps, then records `--profile_steps`. Needs `--max_steps` ≥ timing warm-up + 2 + `--profile_steps` (checked on every rank). The run's timings include profiler overhead, so its row is marked `PROFILED` in `notes` and must not be compared with normal runs |
| `--profile_steps` | 5 | steps recorded |
| `--profile_dir` | `results/profiles` | writes `<job>_<experiment>_<time>_ops.txt` (top 30 operators, committed) and `.pt.trace.json` (timeline for ui.perfetto.dev, git-ignored) |

DDP runs are launched with `torch-python -m torch.distributed.run`; the backend is
NCCL on GPU and gloo on CPU. The world size comes from the launcher, not from a flag.

### `sample.py`

`torch-python src/sample.py --checkpoint <file.pt>` rebuilds the model from the
checkpoint (it imports `GPT` and `GPTConfig` from `train.py`, so the two never drift
apart) and generates text.

| Flag | Default | Meaning |
|------|---------|---------|
| `--checkpoint` | required | `.pt` file from `--save_checkpoint` |
| `--tokenizer` | `data/tokenized/tokenizer.json` | warns if its SHA-256 differs from the checkpoint's |
| `--prompt` | `En un lugar de la Mancha` | |
| `--num_samples` | 3 | |
| `--max_new_tokens` | 200 | stops earlier if the model emits `<\|endoftext\|>` |
| `--temperature` | 0.8 | 0 = greedy (always the most likely token) |
| `--top_k` | 200 | sample only among the k most likely tokens; 0 = no limit |
| `--seed` | 1337 | same seed + same checkpoint = same samples |
| `--device` | `cpu` | |

## 4. `results/runs.csv`

Full spec: `results/README.md` (33 columns, timing method, exposed-communication
method). `src/runlog.py` holds the column list and refuses rows that do not match
it, so `results/README.md` and `runlog.COLUMNS` always change together.

- Only `train.py` (rank 0) appends rows. Nobody adds or edits rows by hand.
- `run_id` is `<slurm_job_id>_<n>` (outside Slurm `local-<YYYYmmddHHMMSS>_<n>`),
  where `n` is the number of rows that job already has in the CSV
  (`runlog.next_run_id`). The runs of a bundled job therefore get `_0`, `_1`, `_2`, …
  This assumes the runs of one job write one after another, which all our jobs do.
- `results/runs.csv` holds experiment runs only (jobs A–E, `opt`, `final`).
  Smoke and development runs (`--job smoke`, `--job dev`) go to
  `results/smoke_runs.csv`, which is git-ignored; their evidence is the Slurm log.
  `train.py` does not redirect them automatically: the caller passes `--runs_csv`.
- A run that crashes gets a row with `status = failed`. A job that never runs
  gets a row with `status = SKIPPED` and the reason in `notes`. No row is ever deleted.
  A run that stops before training starts (e.g. missing `.bin` files) writes no row;
  its evidence is the Slurm log and the job's `FAILED` state.
- `valid` is left empty by `train.py`. Only `src/check_correctness.py` writes it,
  and it writes nothing else.

## 5. Correctness rule and run conventions

**Rule** (README): a run is valid if its validation loss after 500 steps is within
2% of the single-GPU fp32 baseline, same seed, same global batch.

Operational definition used by `src/check_correctness.py`:

- **Baseline rows:** `precision = fp32`, `world_size = 1`, `status = ok`, non-empty
  `val_loss_500`.
- **Matching:** a run is compared with the baseline rows that share `n_layer`,
  `n_embd`, `n_head`, `seq_len`, `global_batch`, `seed`, `steps`, `device` and
  `gpu_model`. `steps` is `--max_steps`: the cosine learning-rate schedule ends at
  `max_steps`, so the learning rate at step 500 depends on it.
  The reference is the **median** `val_loss_500` of those rows.
- **Test:** `|val_loss_500 − reference| / reference ≤ 0.02` → `yes`, otherwise `no`.
  Baseline rows are tested against their own median, so a baseline that disagrees
  with its repeats is flagged too.
- **`n/a`:** `status` is not `ok`, `val_loss_500` is empty (run shorter than 500
  steps), or no matching baseline exists (the printed reason names the columns that
  differ from the closest baseline). The reason is printed, not stored.

Consequences for the experiment plan:
- Any run that must pass the rule needs ≥ 500 steps and an fp32 single-device
  baseline with identical settings on the same device.
- Runs checked against the rule use **`--max_steps 500`**, like the Job A baseline.
  They also keep the default `--lr`, `--min_lr` and `--warmup_steps`: these change
  the loss at step 500 too, but `runs.csv` does not record them, so the checker
  cannot catch a mismatch.
- Job B needs its own fp32 baseline on julia; it is not judged against haskell.
- The Job A sequence-length sweep (100 steps) gets `n/a`: it is a timing
  measurement, not a correctness check.
- The final run (job `final`) is longer than 500 steps, so it gets `n/a`; it is
  judged by its loss curve and its samples, not by the 2% rule.

**Conventions**

| Item | Convention |
|------|------------|
| Seed | 1337 for every run unless an experiment varies it on purpose |
| Repeats | 3 per configuration; analysis uses the median |
| `experiment` labels | lowercase, `_`-separated, repeat index last: `baseline_fp32_r1`, `baseline_bf16_r2`, `seqlen512_fp32_r3`, `ddp_ws2_r1`, `ddp_p2p_off_r1`, `crossnode_ws2_r1`, `cpu_threads16_r1`, `opt_<name>_r1`, `final` |
| Checkpoints | `checkpoints/<experiment>.pt` (git-ignored); only the final run and deliberate tests save one |
| Python on the cluster | `module load pytorch/2.8.0`, then run every script with `torch-python` |
| Where to run | Slurm jobs only; never on the login node |
| Slurm account / QoS | not set; the cluster assigns them (assignment §7) |
| Logs | `#SBATCH --output=slurm/logs/<name>_%j.out`; every log is committed |

**Environment variables** set by the Slurm scripts (recorded for reproducibility):

| Variable | Value | Set in |
|----------|-------|--------|
| `OMP_NUM_THREADS` | `$SLURM_CPUS_PER_TASK` (halved per rank for 2-process CPU DDP) | all training scripts |
| `TOKENIZERS_PARALLELISM` | `true` | `slurm/tokenize.sbatch` |
| `RAYON_NUM_THREADS` | `$SLURM_CPUS_PER_TASK` | `slurm/tokenize.sbatch` |

## 6. Branches and pull requests

- No direct pushes to `master`; everything arrives through a PR.
- One branch per task: `feature/<name>`, `fix/<name>` or `docs/<name>`.
- Keep PRs small and merge often. Persons 3 and 4 both edit `train.py`, so they
  rebase on `master` before opening a PR.
- A PR is mergeable when:
  1. it follows this file (flag names, file paths, CSV columns, data format);
  2. `slurm/cpu_smoke.sbatch` passes on the branch (link the job ID in the PR);
  3. Person 6 has approved it, plus the owner of any file it changes.
- A PR that changes an interface edits this file in the same PR and starts its
  title with `[interface]`.
- Slurm logs that serve as evidence are committed in the PR that produced them.
