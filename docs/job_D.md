# Job D: cross-node DDP (fortran + julia)

Script: `slurm/job_D_crossnode.sbatch`. Owner: Icíar (DDP and instrumentation).
Results: `results/summary.md`, section "Job D" (generated by `src/summarize_results.py`).

## What it measures

The same DDP training as Job C (2 GPUs, global batch 64 = 32 per GPU, 500 steps, seed
1337), but the two GPUs are on **different nodes**, so every gradient all-reduce goes over
the network between `fortran` and `julia` instead of through host memory (SHM, Job C).
Both nodes have the same GPU (RTX PRO 6000 Blackwell), so the 1-GPU reference is Job B.

| Runs | Precision | Reference |
|------|-----------|-----------|
| probe, 30 steps, `NCCL_DEBUG=INFO` | fp32 | which network NCCL picks (not in `runs.csv`) |
| `ddp_crossnode_fp32_r1..3` | fp32 | Job B `baseline_fp32` (37.8 ms/step) |
| `ddp_crossnode_bf16_r1..3` | bf16 | Job B `baseline_bf16` (13.6 ms/step) |

fp32 and bf16 runs are interleaved so that any change in network load hits both equally.

## Prediction (written before the job ran)

**Data the prediction uses.**
- Model: 13,865,856 parameters. DDP all-reduces fp32 gradients in both precisions
  (autocast computes in bf16 but parameters and gradients stay fp32): **55.5 MB per step**.
  With 2 ranks, a ring all-reduce sends and receives about that much per rank.
- Job B, 1 GPU: forward+backward 36 ms (fp32) / 12.1 ms (bf16), optimizer ~1.3 ms, data
  0.5 ms. With half the batch per GPU, the compute part of a step should be about
  **20 ms (fp32)** and **7.6 ms (bf16)**.
- Job C (same node, SHM): exposed communication 2.8 ms, efficiency 96 %.
- DDP overlaps the all-reduce with backward (~2/3 of forward+backward: ~12 ms fp32,
  ~4 ms bf16), so only the rest is exposed.

**Expected step time by network** (the probe tells us which row applies):

| Network between nodes | All-reduce time | fp32 step | fp32 speed-up | bf16 step | bf16 speed-up |
|-----------------------|----------------:|----------:|--------------:|----------:|--------------:|
| 10 GbE, TCP sockets (~1.1 GB/s)   | ~50 ms | ~60 ms | ~0.6× (slower than 1 GPU) | ~54 ms | ~0.25× |
| 25 GbE, TCP sockets (~2.8 GB/s)   | ~20 ms | ~30 ms | ~1.3× | ~24 ms | ~0.6× |
| 100 Gb InfiniBand / RoCE (~11 GB/s) | ~5 ms | ~21 ms | ~1.8× | ~9 ms | ~1.5× |

**Claims to test, independent of the network:**
1. Cross-node efficiency is lower than Job C's 96 % for both precisions.
2. bf16 has a **lower efficiency and a higher communication share** than fp32, because
   compute shrinks ~3× and the bytes sent do not. This is the main result of Job D.
3. Exposed communication in ms is roughly the same for fp32 and bf16 (same bytes), but
   slightly higher in bf16 because the shorter backward hides less of it.
4. The validation loss at step 500 is within the 2 % rule of Job B (same as Job C: DDP
   changes which windows each rank samples, not the maths).

## Things that can distort the result

- **Busy fortran.** Rank 0 runs on `fortran`, which was heavily loaded by other users
  (CPU load ~400 on 18 Nov). A slow rank makes the other wait at the all-reduce, and that
  wait is counted in `t_comm_ms`. The log prints each node's load average at the start.
- **InfiniBand inside the container.** PyTorch runs in Apptainer. If the IB devices are not
  passed through, NCCL falls back to TCP sockets even if the nodes have IB. The log prints
  `ibstat` and `/sys/class/infiniband` per node and the probe's `NET/...` line says which
  transport NCCL used. Record both in `env/cluster.md`.
- **Init hang.** If NCCL picks the wrong interface, the probe times out (`DDP_TIMEOUT`,
  15 min). Pick the interface from the `ip -brief addr` output and resubmit with
  `NCCL_SOCKET_IFNAME=<interface> sbatch slurm/job_D_crossnode.sbatch`.
