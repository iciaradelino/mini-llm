# mini-llm — training a small GPT on an HPC cluster

Small GPT-style language model (adapted from nanoGPT) trained on a public-domain
Spanish corpus, used to study performance and scaling on the cluster:
single GPU, multi-GPU DDP (intra- and inter-node), and a CPU/OpenMP thread-scaling
comparison.

## Route

| Technology      | Used for                                                     |
|-----------------|--------------------------------------------------------------|
| Slurm           | All jobs (CPU tests, GPU experiments), bundled into few jobs  |
| PyTorch + CUDA  | Single-GPU training, fp32 vs bf16                              |
| PyTorch DDP     | 1→2 GPUs on one node, cross-node DDP, NCCL P2P on/off          |
| CPU / OpenMP    | Thread-scaling experiment (1–64 threads) on the `cpu` partition |
| Profiler        | Bottleneck analysis (data / compute / communication)          |

## Repository layout

## Baseline model

| Parameter        | Value               |
|------------------|---------------------|
| Parameters       | 13.87M              |
| Layers           | 6                   |
| Heads            | 6                   |
| Width (n_embd)   | 384                 |
| Sequence length  | 256                 |
| Global batch     | 64 sequences        |
| Tokenizer        | byte-level BPE, 8,192 tokens |

The global batch is kept fixed for all DDP runs (per-GPU batch = 64 / world size).

## Correctness rule

> A run is valid if its validation loss after 500 steps is within 2% of the
> single-GPU fp32 baseline (same seed, same global batch).

`src/check_correctness.py` applies the rule and fills the `valid` column of
`results/runs.csv`; how runs are matched to their baseline is defined in
`docs/interfaces.md` §5. Runs that fail the rule (e.g. an optimization that
changes numerics too much) stay in `results/runs.csv` with `valid = no` and are
discussed in the report — they are never deleted.

## Measurement rules

- Every run times itself: data loading, forward/backward, optimizer step and
  gradient communication, measured per step.
- The first ~20 steps are warm-up and excluded from timing.
- Each configuration is repeated 3 times; analysis uses the median.
- Each run appends one row to `results/runs.csv` (schema in `results/README.md`).
- Experiments that cannot run (e.g. the cross-node job never gets scheduled) are
  recorded as **SKIPPED** with the reason, not as negative results.
- **Never run training on the login node.** CPU tests go to the `cpu` partition.

## Experiment plan

| Job | Resources              | What it runs                                                   |
|-----|------------------------|----------------------------------------------------------------|
| A   | 1 GPU on haskell       | fp32 baseline ×3, seq-len sweep 128–1024, bf16 ×3, profiler run |
| B   | 1 GPU on julia         | fp32 ×3, bf16 ×3 (GPU generation comparison)                    |
| C   | 2 GPUs on haskell      | DDP ×3, DDP with `NCCL_P2P_DISABLE=1` ×3, profiler run          |
| D   | 1 GPU on each node     | Cross-node DDP ×3                                               |
| E   | CPU only (`cpu`)       | Thread sweep 1,2,4,8,16,32,64 × 3 repeats                       |

See `docs/plan.md` for the full phase-by-phase plan, `docs/interfaces.md` for the
contract between pipeline stages, and `REPRODUCE.md` for exact commands.
